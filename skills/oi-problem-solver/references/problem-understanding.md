# 题意理解与形式化

## 事实台账

开始推导前建立五栏；简短任务可在心中维护，歧义任务应显式展示。

1. **用户明确给出**：原话可定位的输入、操作、目标、范围、样例。
2. **原题可确认**：从用户提供的完整题面／可信原始页面直接取得；记录来源版本。
3. **逻辑推出**：由前两栏必然推出的事实，写出推导。
4. **工作假设**：为分支分析暂取的解释，绝不称为题面条件。
5. **未知**：无法确定且可能改变算法、证明、复杂度或实现的内容。

外部题解只是解释／候选解法，不升级为原题条件。图片或 PDF 转写不清的符号先标不确定。

## 规格清单

逐项检查：

- 输入对象、下标、数值域、是否多测及总规模；
- 操作的时序、在线／离线、是否持久化、操作间依赖；
- 重复元素、重边、自环、空对象、平局、负值是否允许；
- 数组／区间是闭、开还是半开，编号从 0 或 1；
- 图有向性、连通性、权值限制；树的根是否固定；
- 输出是任意可行、计数、最优值、方案还是多字段；
- 取模、精度、随机错误是否允许；
- 时间、内存、栈、语言和交互／特殊 Judge 条件。

## 形式化

把自然语言写成：输入集合 `I`、合法性谓词 `Valid(x)`、输出关系 `Accept(x,y)` 或目标函数、规模参数与限制。对于操作序列，写状态 `S_t`、操作前提和 `S_t → S_{t+1}`。对于优化问题，明确最小／最大方向和无可行解语义。

样例只能检查当前解释的一致性，不能补出样例未区分的规则。若两种解释都符合样例，分别说明：

- 解释 A/B 的差异；
- 对用户算法的影响；
- 哪一条原文能消歧，或需要用户补充什么。

## 完整性检查

在开始复杂算法前，尝试为最小合法规模手算输入输出。若连 `n=0/1`、单点、单边或空查询的正确答案都无法定义，先处理规格缺口。不能为了让用户思路成立而缩小输入域，也不能用代码中的数组大小反推题目范围。
