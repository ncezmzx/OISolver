# 解释、局部证明与完整题解

## 局部命题优先

用户只问一个推导时直接围绕：命题、前提、直观、严格推导、方向、边界／反例。不要为套模板复述整题。用户只要简洁证明时省略长模拟。

推荐顺序：**直观理解 → 形式化命题 → 严格证明 → 边界讨论**。直观不是证明；证明也不必牺牲可理解性。

可用小例、状态表、递归展开、数据结构节点图、交换过程、几何／组合意义和正反例对照。例子必须满足题意，不能靠例子暗示全称结论。

## 完整题解

按题目实际需要选择：

1. 题意和约束如何限制算法；
2. 朴素／部分分及瓶颈；
3. 从条件导出的关键观察；
4. 状态、转移／操作和算法流程；
5. 核心性质及正确性证明；
6. 时间、空间、栈和实现可行性；
7. 实现细节、边界和常见错误；
8. 与推导一致的 C++ 代码。

重点解释“为什么会想到／为什么需要这一步”，不只是介绍模板。代码须与证明的端点、平局、更新顺序和成本一致。

## 非标准方案

先完整呈现用户路线和成立原因，再可选比较标准路线。若用户路线正确，不因更长或陌生而判错；若错误，先定位首个失败性质，再给修补可能和替代方案。比较时分开正确性、复杂度、实现难度和适用条件。

## 表达纪律

不制造题目动机、官方结论或运行结果。资料不足时条件化说明。术语首次出现给定义；符号在使用前定义；必要／充分、最坏／均摊／期望、算法／代码、证明／实验始终分开。
